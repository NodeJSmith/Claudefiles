## Contradictions

**1 minor — T02's wiring instruction is imprecise about pipeline position (not a hard contradiction, but a real ambiguity risk).**

- `design.md` Architecture states the canonical order: *"Order: opkg install → color strip → dispatch rewrite (skills + commands + agent bodies) → model remap (agent frontmatter only, anchored) → worker agent generation → config.json generation → lint."*
- `T01` (`tasks/T01-script-skeleton.md`, Prompt point 7) lays down stub markers in that exact order: *"strip colors → (placeholder for dispatch rewrite, T03) → (placeholder for model remap, T03) → (placeholder for worker generation, T02) → (placeholder for config generation, T02) → (placeholder for lint, T04) → record sync SHA → done message."*
- `T03` (`tasks/T03-dispatch-rewriter.md`, "Wire into main()") restates the same canonical order verbatim: *"The pipeline order per the design: opkg install → color strip → dispatch rewrite (skills + commands + agent bodies) → model remap (agent frontmatter only, anchored) → worker agent generation → config.json generation → lint."*
- `T02` (`tasks/T02-tier-map-and-generation.md`, "Wire into main()") instead says: *"Call `generate_worker_agents()` and `generate_config()` at the T02 stub points in `main()`, **after color field stripping** and before the lint stub."*

T02's phrasing is technically true (worker-gen *is* after color-stripping and before lint) but omits that two T03 stub points (dispatch rewrite, model remap) sit between color-stripping and the T02 stub point. An implementer following T02's wording in isolation — without cross-referencing the already-placed `# T02: worker agent generation` comment from T01 — could plausibly insert the calls immediately after `strip_color_fields()`, ahead of T03's stubs, inverting the canonical pipeline order. Since T02 is executed before T03 in the `depends_on` chain, this is the one point in the plan where a careless read could produce a wrong wiring order that a later task doesn't re-verify. Not severe (T01's comment markers, if respected literally, prevent it), but worth tightening in T02's wording before execution.

## Non-Local Criteria

The design doc's Test Strategy is explicit: *"Verification against the live OpenCode install. No formal test framework for the sync script exists... Gap: no isolated test fixture for OpenCode. Tests run against the live `~/.config/opencode/` directory... accepted gap for now."* That decision propagates into nearly every task's `Verify` checklist as criteria that require mutating/reading the real global `~/.config/opencode/` (and, for T04, the user's real `opencode.jsonc`), not just repo state:

- **T01**: AC#4 (mtime of live `opencode.jsonc`), AC#10 (`--check` against live sync-state file), FR#10/AC#12 (grep on live `~/.config/opencode/agents/`)
- **T02**: AC#1, AC#2, AC#3, FR#1, FR#2 (all require inspecting generated files under live `~/.config/opencode/agents/` and `~/.config/opencode/config.json` — dry-run-output checks are the closest thing to local, but the "after sync" phrasing of FR#1/FR#2's non-dry-run verify items is explicitly post-install)
- **T03**: AC#5, AC#6, AC#9, AC#11, AC#16, AC#17 (all grep live `~/.config/opencode/{skills,commands,agents}/`)
- **T04**: AC#7, AC#8, AC#13 (lint run against live installed output), AC#15 (depends on the *actual* content of the user's live `opencode.jsonc`, which is machine-specific and not reproducible from the repo alone), AC#18 (requires a pre-existing foreign `config.json` planted in the live directory)

**T05 is the one task whose `Verify` item is fully local** — `grep -q 'subagent_depth' REFERENCE.md` and `grep -q 'PRAGMA busy_timeout' REFERENCE.md` run against repo files.

This is a disclosed, deliberate scope decision (roadmap Spec 1 — "isolated test fixture" — is explicitly deferred, per design.md Non-Goals), not a silent gap. Flagging it here because it is the sole reason this plan cannot reach a strict PASS: verifying T01–T04 as written requires a machine with a real OpenCode install and a willingness to overwrite that machine's live global config, which is not reproducible or automatable in CI or in a fresh checkout.

## Warnings

1. **T05 introduces a SQL schema not present anywhere in `design.md`.** T05's Prompt supplies a literal query (`SELECT s.id, s.model_id, a.name as agent_name FROM sessions s LEFT JOIN agents a ON s.agent_id = a.id WHERE s.parent_id IS NOT NULL ORDER BY s.created_at DESC LIMIT 20;`) against columns (`model_id`, `agent_id`, `parent_id`, `created_at`) that `design.md` never confirms. Design.md's Test Strategy only describes the query generically ("SQLite query against `~/.local/share/opencode/opencode.db` for child session model verification") and its Dependencies section flags other OpenCode internals as "verify before implementation" but does not extend that caveat to this schema. If the actual `opencode.db` schema differs, T05 will ship an incorrect documented query with no task catching the mismatch (T05's own Verify only checks that the string `PRAGMA busy_timeout` appears in REFERENCE.md, not that the query is correct against a real DB).

2. **Several Behavioral Invariants named in `design.md` have no corresponding AC/Verify item.** design.md's "Behavioral Invariants" section lists: `--allow-worktree` must still permit running from a worktree; named agents must still have correct model mappings in frontmatter after sync; the sync must still uninstall previous opkg output before reinstalling. None of these map to a numbered AC, so per the "only report gaps for identifiers in the design doc" instruction they are not counted as coverage Gaps — but they are also absent from every task's `Verify` checklist (T01's Focus section mentions porting the opkg-uninstall check and the worktree-detection logic, but no task treats them as checkable exit criteria). Behavior only, no missing FR/AC.

3. **AC#11's grep pattern doesn't structurally implement its own stated qualifier.** design.md's AC#11 text is: *"After sync, `grep -r 'model:.*sonnet\|model:.*haiku\|model:.*opus' ~/.config/opencode/skills/` returns zero matches **for lines that also reference a named agent type like `code-reviewer`** (FR#9)."* The grep command shown matches *any* line with a bare `model:` tier string, not specifically lines that also reference a named agent type — the qualifier is a natural-language gloss the literal command doesn't encode. This is inherited verbatim into T03's Verify checklist (unchanged), not introduced by the task file. In practice this is likely benign (after a clean sync no bare Claude-tier `model:` string should survive in skill body content at all, named-agent-adjacent or not), but as written the criterion is looser than its own English description promises.
