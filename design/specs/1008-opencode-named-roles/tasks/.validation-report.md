## Warnings

- **FR#5 (T01) is loosely worded as a standalone criterion.** "Both worker bodies contain dispatch-discipline content and no task-specific process content" requires a content-quality judgment that isn't purely mechanical. This is materially mitigated by AC#4 in the same task, which gives a concrete mechanical check (`grep -c 'mine-' agents/light-worker.md agents/standard-worker.md` returns 0) — but FR#5's own Verify line, read in isolation, is not binary-verifiable.
- **FR#12 (T01) is loosely worded as a standalone criterion.** "Every agent's `tools:` list is widened" has no baseline stated in the Verify item itself (widened relative to what?). Mitigated by AC#19 in the same task, which supplies the concrete floor (`Read`, `Write`, `Edit`, `Bash`, `Grep`, `Glob`), and by the second clause of FR#12's own Verify line ("no agent body or description still claims to be read-only"), which is independently grep-checkable.
- **T03's `depends_on: ["T01"]` is not obviously required by content.** T03 (escalation removal) doesn't appear to read or write anything T01 creates — the design's own rationale for T03-before-T04 ordering ("the text it deletes contains `general-purpose` references that would otherwise be migrated and then immediately removed") only explains T03-before-T04, not T01-before-T03. This is not a defect (T01→T03→T04 is a valid serialization and doesn't block correctness), but it does forgo the T02/T03 parallelism that the dependency graph would otherwise allow, since both only need T01. Worth confirming with the planner whether this was an intentional sequencing choice or an unnecessary dependency.
