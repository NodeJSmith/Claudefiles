## Contradictions

**1. T01 instructs adding an index on `gate_id` that design.md explicitly forbids.**

`design.md:230` (Architecture → The findings table):
> "Plus `idx_findings_run ON findings(run_id)`, matching the run-scoped index shape `questions` uses. No index on `source` — with a single producer (`challenge`) the index is pure overhead; add it when a second producer materializes. **No index on `gate_id`** — `dispatches.gate_id` is unindexed despite `bin/agent-stats:135` joining on it, and at roughly seven rows per challenge run SQLite will not care."

`T01-findings-table-and-module.md` (Prompt, §1, item 2):
> "...The table has columns: ... `resolved_at`, `created_at`. **Plus indexes `idx_findings_run ON findings(run_id)` and `idx_findings_gate ON findings(gate_id)`.**"

T01 tells the executor to create an `idx_findings_gate` index on `findings.gate_id`, which the design doc's DDL rationale section explicitly says NOT to add, with a stated reason (parity with `dispatches.gate_id`, negligible row count). This appears to stem from an internal inconsistency in design.md itself — the Migration section (`design.md:292`) says "creates the `findings` table and its **two indexes**," which is inconsistent with the DDL rationale section that describes only one index (`idx_findings_run`) as actually created. T01 resolved that ambiguity by inventing a second index, but did so in direct conflict with the more detailed, explicit "No index on `gate_id`" prohibition and its stated rationale. This is a genuine contradiction between the task and the design's explicit constraint, regardless of which design.md passage the planner was reconciling.
