# Synthesis Procedure

The synthesis subagent reads this file and follows it exactly. The dispatching prompt supplies the critic report paths, triage rationale, `target_summary`, target type, output path, and validation warnings; everything about *how* to synthesize lives here, so it reaches the subagent verbatim instead of through the orchestrator's summary of it.

1. **Read all critic reports in full** — do not glob; read each named file explicitly.
2. **Group by problem area** — cluster findings addressing the same concern. Keep similar-but-distinct issues separate.
3. **Assign tags per finding:**
   - `severity`: highest severity any critic assigned (must be CRITICAL / HIGH / MEDIUM / TENSION — reclassify non-contract values as MEDIUM)
   - `type`: type best describing the root cause
   - `design-level`: Yes wins when critics disagree
   - `likelihood`: how often the problem actually occurs for this project, judged from the critics' `When it bites` and the project context. Likelihood rates failures, and a problem in the code's shape isn't one: a rule living apart from the code it protects, one value with two owners, a lifecycle split across functions, a docstring that misdescribes the code. Those exist on every run and every read, so they are `routine` even if they never cause a bug. Ask whether the complaint would still stand if nothing ever went wrong. If so, rating it `rare` would present a present-tense cost as an unlikely event and steer it toward being accepted. `routine`: normal use hits it, or the problem is the code's shape. `plausible`: a realistic non-normal path hits it (a restart, a timeout, bad input from a real source). `rare`: it needs an unusual coincidence (a narrow race window, a crash mid-write, a flapping link, a misconfiguration nobody makes), or it only matters for a different audience or scale (every `Audience assumption:` finding). Judge it yourself rather than taking the critic's word: critics argue for their findings, and a fix for a rare case is permanent code that every later reader carries. A CRITICAL finding is never `rare`. When torn between `plausible` and `rare`, pick `plausible`: a wrong `rare` steers the user toward leaving a real problem unfixed, while a wrong `plausible` only costs them one more question.
   - `classification`: Auto-apply only when ALL critics agree on the same fix AND it's localized and additive AND severity is not CRITICAL AND likelihood is not `rare` (a rare finding goes to the user as a candidate known limitation, never silently patched) AND the fix adds no state, setting, validator, or new mechanism and no guard, reset, or heuristic by which one component guesses at another's state (a fix like that can become the next root cause, so the user sees it). Otherwise User-directed. When ambiguous, default User-directed.
   - `visibility`: `presented` for every finding
   - `disposition`: `pending` for every finding
4. **CRITICAL guard**: classify every CRITICAL finding as `classification: User-directed`, whatever any critic proposed and however much they agreed — a fix to a broken core requirement needs the user's decision.
5. **Copy presentation fields** from critic reports: `why-it-matters` (most concrete consequence statement, keeping any critic's `Audience assumption:` opening verbatim), `when-it-bites` (the trigger, restated in your own judgment of how often it happens), `evidence` (all file:line citations, deduped), `design-challenge` (strongest question). Write `not cited` for evidence when none; omit other fields when absent.
6. **Write the reasoning, then the recommendation**, following `${CLAUDE_CONFIG_DIR:-~/.claude}/references/common/presenting-decisions.md`. For each User-directed finding, in this order: `deciding-factor` (what the recommendation optimizes); a `criteria` table scoring every option on the same criteria; then the `recommendation` (which option and why) and a `pick-instead-if` condition for every option you don't recommend. Fill in the table before choosing — a table written after the pick only argues for it. When a proposed fix adds state, a setting, a validator or guard, or a new mechanism, first ask whether the setting or code path that causes the problem needs to exist; if it could be deleted, deleting it is an option and comes first. Such a finding's criteria also include whether the fix's ongoing cost is worth how often the problem occurs. For a problem in the code's shape, the options include the fix that puts the piece where it belongs, even when no critic proposed it, since critics tend to patch the shape they found. User-directed findings' criteria include what peers do about the problem, because critics argue for handling what they found and peers routinely leave the same case unhandled. Take it from the prior-art brief named on the target's `**Prior art:**` line when there is one, then the CLAUDE.md `peers:` frontmatter or comparable projects you can name in a public repo; write `unknown` rather than guess, and drop the row in a private repo with no `peers:` declared. For a `rare` finding other than a TENSION or convergence finding (those keep their own option shapes), offer at most two fix options (deleting the cause counts as one, and is dropped when it amounts to accepting the limitation), and the last option is always `Accept as a known limitation: <the limitation in one clause>`, which is the recommendation unless the consequence is silent data loss, a security hole, or a state the user can't recover from without editing files by hand. Accepting is a real outcome, not a skip: for a small project, a documented limitation usually costs less than the code that guards against it. For TENSION: `deciding-factor`, a `criteria` table with one column per side, and a `pick-instead-if` for each side; no recommendation.
7. **Validity assessment**: assess whether each finding holds up. Findings are valid by default — to flag one as likely invalid, you must provide concrete evidence: what the finding claims, what the code actually does, and why they conflict. Read the relevant code to verify claims. If you cannot articulate the evidence trail, the finding stays in the main list. Move likely-invalid findings to the `## Likely Invalid` section per the findings protocol; set each moved finding's `visibility` to `likely-invalid` and drop its `disposition` (omit the field — NULL). Renumber the remaining findings to stay contiguous (no gaps in the `## Finding N:` sequence).

8. **Convergence check**: step 2 groups findings that describe the *same* concern. This step looks one level up — at distinct findings that all land on the *same mechanism* (one component, piece of state, protocol, or loop) from different angles. Each such finding proposes its own local fix; together they can mean the mechanism itself is the problem, and patching each one hardens a model that should be reconsidered. Use your judgment: there is no minimum count, and findings that merely touch the same file are not a convergence. A real convergence names one specific change to the mechanism that would make at least two members' local fixes unnecessary; findings that share a subject but would each still need their own fix are not one. Distinct findings from different critics landing on one mechanism is the strongest signal. A finding belongs to the convergence when its problem is in the mechanism *or* its proposed fix adds a rule, guard, or reset to the mechanism — a finding that patches the mechanism is evidence about it even when its symptom shows up elsewhere.

   For each convergence you identify, add a **convergence finding** to the main list:
   - Title: `Findings converge on <mechanism>`
   - `severity`: highest severity among the converging findings. `likelihood`: the most likely among them (`routine` over `plausible` over `rare`). `type`: `Structural`. `design-level`: `Yes`. `classification`: `User-directed`. `raised-by`: `Synthesis`.
   - `**Converges:**` field listing the converging finding numbers, formatted as `**Converges:** Findings 3, 5, 7`.
   - `why-it-matters`: name the mechanism and what the converging findings have in common. Frame it as a question for the user: whether this points to a structural or architectural problem with the mechanism that should be re-evaluated, rather than addressed finding by finding. Re-evaluation is open-ended — it includes whether the mechanism is needed at all, and whether the failure modes are worth handling or are a limitation to accept and document, not only how to specify it more completely.
   - Options: **A** — re-evaluate `<mechanism>` before addressing the converging findings individually; **B** — keep `<mechanism>` and address the converging findings individually. Option A may list the open questions the re-evaluation must answer, but must not answer them — no proposed design, scope, owner, or rule. Answering them here pre-empts the re-evaluation with a patch.
   - The remaining fields follow steps 5–6 like any User-directed finding: `evidence` (the key citations from the converging findings), `design-challenge`, and a `**Recommendation:**` with the `*(recommended)*` marker on whichever option the evidence supports.

   Place convergence findings first in the main list, then renumber so every finding (and every `**Converges:**` reference) stays contiguous and correct. Leave the converging findings themselves in the list unchanged — they are resolved individually if the user picks B. Before writing, confirm every `**Converges:**` number matches an existing `## Finding N:` heading: a stale number makes the resolution flow skip the wrong finding.

**Write the findings file** to the output path using the `Format-version: 4` header. Include `**Likely-invalid:** N` in the header block (even when 0). Format per `${CLAUDE_CONFIG_DIR:-~/.claude}/skills/mine-challenge/findings-protocol.md`.
